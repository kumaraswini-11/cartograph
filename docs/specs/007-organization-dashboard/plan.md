# 007 — Organization dashboard: plan

**Spec:** [spec.md](spec.md)
**Status:** Approved

## Approach

Storage is Supabase's Postgres (`docs/adr/0001`), reached with the Clerk
token `006` already attaches to every request. Who may read a row is
decided by the database, from the token's organization claim, never by the
application (C-02): every table has row-level access, switched on by the
database itself whenever a table is created (C-01), and every table's rows
belong to an organization through a required reference that deleting the
organization follows (FR-001, FR-002).

Everything storage owns moves into its own package, `@workspace/database`, as
`006` planned (`006` plan D-08): the migrations, the policies and the
database tests that prove them, the generated table types, the client and
the queries. The web app keeps what's about the web: reading Clerk's token,
the dashboard's server function and its interface.

The policies are tested against a real Postgres, Supabase's local stack in
Docker, locally and in CI, with tokens shaped like Clerk's. Deployed
environments get their schema only from migrations: a staging project for
preview deployments, production for `main`, each updated by CI (C-03).

## Data

```sql
-- Every organization that owns rows, keyed by Clerk's organization ID.
organizations (
  id text primary key,                        -- the token's o.id
  created_at timestamptz not null default now()
)

-- An organization's map of one repository (CONTEXT.md: Analysis).
analyses (
  id uuid primary key default gen_random_uuid(),
  organization_id text not null references organizations on delete cascade,
  repository text not null,                    -- "owner/name"
  created_at timestamptz not null default now(),
  unique (organization_id, repository)         -- at most one per repository
)

-- One pass over a repository (CONTEXT.md: Run, Stage).
runs (
  id uuid primary key default gen_random_uuid(),
  organization_id text not null references organizations on delete cascade,
  analysis_id uuid not null references analyses on delete cascade,
  state text not null check (state in ('fetching', 'parsing', 'storing', 'done', 'failed')),
  started_at timestamptz not null default now(),
  finished_at timestamptz
)
-- An index on every organization_id, and on runs (analysis_id, started_at desc).
```

Every policy has the same shape, Supabase's Clerk example:
`to authenticated using (organization_id = (select auth.jwt()->'o'->>'id'))`.
`organizations` compares its `id` instead. `runs` carries its own
`organization_id` rather than reaching it through `analyses`, so its policy
reads one indexed column, as Supabase's guidance on policy performance asks.
`008` adds what a run stores beyond its state.

## Decisions

- **D-01** A package of its own, `@workspace/database`, holding Supabase's
  project folder through the CLI's `--workdir`. _Why:_ Turborepo's "one
  purpose per package"; the database tests and type generation become this
  package's tasks, which Turborepo runs and caches, and only packages that
  declare it can reach storage (`006` plan D-08). Named for what it holds,
  the database where storage lives (CONTEXT.md), as Turborepo's own example
  names its `@repo/database`. _Rejected:_ Supabase's default `supabase/` at
  the repository root, which no package owns; `@workspace/storage`, which in
  a Supabase codebase reads as Supabase Storage, its file product
  (`client.storage`); `@workspace/db`, an abbreviation this repository's
  package names don't use.
- **D-02** Row-level access is switched on by the database for every table
  created in `public`: Supabase's documented event trigger, `ensure_rls`,
  is the first migration (C-01). `supabase db advisors --fail-on error` in
  CI catches a table that somehow has it off, and AC-04's test reads every
  table from the catalog. _Why:_ Supabase has no project setting for it; the
  trigger is its documented way. The trigger's function sits in a schema the
  API doesn't expose, with `search_path` set, as Supabase advises for any
  `security definer` function.
- **D-03** The default grants Supabase gives `anon` and `authenticated` on
  every new table are revoked, and each table grants `authenticated` only
  what it needs. _Why:_ Supabase is changing its platform default to the
  same, and "adding policies doesn't take those grants back"; and from
  2026-10-30 new tables are no longer exposed to its Data API unless
  granted (Supabase changelog, 2026-04-28), so every grant is written out. So a table
  with no policy yet answers with nothing: no rows, or a permission error,
  never data (FR-004, AC-05 accepts either).
- **D-04** A tenant table, `organizations`, that every other table
  references, `not null`, `on delete cascade`. _Why:_ AC-08 becomes a
  constraint the database enforces rather than a habit, and deleting an
  organization is one delete that reaches every table, including ones later
  specs add (FR-002). Its rows are added when an organization first stores
  something (`008`) and by the seed; none exist yet in deployed
  environments.
- **D-05** Three environments. Local: Supabase's stack in Docker, for
  development and the database tests. Staging: a second cloud project, the
  previews' storage. Production: the current project. Migrations reach the
  cloud only through CI (`supabase db push`): a pull request's to staging,
  `main`'s to production (C-03). _Why:_ Supabase's documented setup;
  branching is paid. AC-09 compares production's schema with one built from
  the migrations (`supabase db diff --linked`).
- **D-06** The policies are proved by pgTAP tests run with `supabase test
db`, each in a transaction that's rolled back, with Clerk-shaped claims
  set through `request.jwt.claims` (which is what `auth.jwt()` reads), and
  the role set to `authenticated`. AC-03, AC-04 and AC-08 enumerate every
  table from Postgres's catalog, so a table added later is covered without
  touching the tests. Written as Supabase's RLS guide asks: a refused write
  asserts `42501`, a filtered read asserts zero rows. _Why not Supabase's
  community test helpers:_ they create Supabase Auth users, which this
  project doesn't use.
- **D-07** Deleting an organization's records: a public webhook route takes
  Clerk's `organization.deleted`, checks its signature with Clerk's
  `verifyWebhook` (`CLERK_WEBHOOK_SIGNING_SECRET`), and deletes the
  organization's row with Supabase's secret key, which cascades. _Why:_ no
  signed-in person makes this request, so no token for a policy to read;
  Supabase's secret key is its documented way, used server-side, by this
  module only, and never with a user's token ("a secret key bypasses RLS
  only when the request carries no user access token"). Deleting a row
  that's already gone deletes nothing, so a repeated or late notice is safe
  (Clerk delivers at least once, out of order). Not a read, so C-02 is
  untouched.
- **D-08** Sample analyses come from a seed script for one organization
  (yours, by its ID), run against the local database only; it refuses any
  address but the local stack's (C-04). _Why not `supabase/seed.sql`:_ the
  rows must belong to a real Clerk organization to be visible to its
  token, and its ID isn't known to a file in the repository.
- **D-09** The dashboard asks one question, `listAnalyses`, with no
  organization in it: PostgREST returns each analysis with its latest run
  (an embedded `runs`, newest first, limited to one), and the policies
  decide whose rows those are (C-02). Switching organization reruns the
  same loader with the new token (AC-02). Each run state shows as a text
  badge, never by colour alone (WCAG 2.2, 1.4.1).

## What needs doing outside the code

By the repository's owner:

- **Docker Desktop** running, for the local stack.
- **Supabase:** a second project, "cartograph-staging", with Clerk added as
  a third-party provider and its own sign-up off, as production has.
- **GitHub Actions secrets:** `SUPABASE_ACCESS_TOKEN`, and for staging and
  production each, the project ID and database password.
- **Vercel:** Preview gets staging's `SUPABASE_URL` and keys, Production
  production's; both get `SUPABASE_SECRET_KEY` (secret) and
  `CLERK_WEBHOOK_SIGNING_SECRET` (secret).
- **Clerk:** a webhook endpoint for `organization.deleted` at production's
  `/api/webhooks/clerk`.

## Testing

- pgTAP (`supabase test db`), locally and in CI: AC-03 to AC-06, AC-08.
- Supabase's checks in CI: `supabase db advisors --local --fail-on error`;
  the generated types unchanged.
- Vitest: `listAnalyses` sends no organization (C-02, AC-02); the webhook
  refuses a bad signature and deletes on a good one.
- Terminal: AC-09, production's schema against the migrations.
- Browser, then on the preview: AC-01 and AC-07, and switching.

## Risks

- **Docker in CI and locally** → Supabase's own CI recipe runs on
  `ubuntu-latest`; locally, Docker Desktop must be running.
- **A deleted organization's rows linger until Clerk's notice arrives** →
  accepted in the spec's edge cases; no token can read them meanwhile.
- **Staging and production drift** → only CI pushes migrations, and AC-09
  checks production against them.
- **One Clerk instance for every environment (`006` D-10)** → its deletion
  webhook points at production; staging's leftover rows are test data.
